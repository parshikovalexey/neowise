# Тестовое Neowise. AI-помощник для входящих заявок

Ориентир — 45–60 минут. Менеджер вводит текст заявки, получает тему и черновик ответа. Он читает результат и сам решает, что отправить клиенту.

## Запуск

В репозитории есть сервер, HTML-страница и имитатор модели. Нужен Node.js 20 или новее. Зависимостей и ключей нет.

```sh
node server.mjs
```

Откройте http://127.0.0.1:3000. Порт можно задать через переменную `PORT`.

## Тест

```sh
node --test
```

Тест сам поднимает `server.mjs` на порту 3987, дожидается готовности, прогоняет сценарии и печатает по каждой проверке строку с `✔` или `✖` (в конце — сводка `pass`/`fail`). Зависимостей не требует. Проверяется:

- страница `GET /` — 200, HTML и форма разбора;
- сбои модели: `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` → HTTP 200 и ровно `{"status":"manual_review","topic":null,"draft":null}`, причём ответ на `[timeout]` приходит быстрее 900 мс (лимит ожидания модели — 300 мс, имитатор отвечает за 1200 мс);
- запись сбоя в серверный лог: `reason=timeout`, `reason=provider_error`, `reason=invalid_output` и текст заявки;
- валидация входа: пустой, пробельный, отсутствующий и нестроковый `text`, битый JSON, не-объект и тело больше 64 КБ → HTTP 400 `{"status":"invalid_input"}`;
- неизвестные маршруты и методы → 404;
- успешный разбор: точный набор полей `status`/`topic`/`draft` и все три темы — `delivery`, `pricing`, `other`.

Лог сбоев сервера тест печатает в консоль по ходу прогона (stderr) — строки `[triage] … failure reason=… text=…` появляются рядом со строками проверок. Чтобы увидеть их подробнее, добавьте `--test-reporter=spec`; лог также пишется при обычном запуске приложения.

## Лог сбоев

При сбое модели менеджер получает только `manual_review`, поэтому настоящая причина пишется в stderr сервера одной строкой вместе с текстом заявки:

```
[triage] 2026-11-23T10:00:00.000Z failure reason=timeout detail=AbortError: The operation was aborted text="[timeout] клиент ждёт ответа"
```

`reason` — одно из `timeout` (не уложились в 300 мс), `provider_error` (имитатор/провайдер бросил исключение), `invalid_output` (ответ не JSON, недопустимая тема, пустой черновик). По тексту заявки в логе видно, на каком запросе это произошло.

## Что изменить

1. Доработайте `POST /api/triage`. Принимайте JSON с полем `text`, содержащим непустую строку. При пустом, отсутствующем, нестроковом вводе или битом JSON верните HTTP 400 и `{"status":"invalid_input"}`.
2. При корректном ответе модели верните HTTP 200 и `{"status":"ready","topic":"…","draft":"…"}`. Допустимые темы — `delivery`, `pricing`, `other`. Черновик должен быть непустой строкой. При таймауте, ошибке модели или неподходящем ответе верните HTTP 200 и `{"status":"manual_review","topic":null,"draft":null}`. Ограничьте ожидание модели 300 мс. Оставьте поведение выданного имитатора прежним.
3. Покажите на странице тему и черновик при успехе. Для `manual_review` покажите понятное сообщение менеджеру и очистите предыдущий черновик. Добавьте хотя бы один исполнимый тест для поведения при сбое и инструкцию его запуска.

Для локальной проверки имитатор принимает любой обычный текст. Метки `[timeout]`, `[error]`, `[bad-json]`, `[bad-topic]`, `[empty-draft]` включают отдельные сценарии сбоя.
